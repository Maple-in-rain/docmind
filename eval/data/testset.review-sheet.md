**出处段落**（检查答案是否确实出自此段）：

> RESTful API 中状态码要区分语义：认证失败用 401 而不是 400；参数校验失败用 400 还是 422（Unprocessable Entity，语义是"格式对但内容不合法"）取决于团队规范；限流建议 429 并携带 Retry-After 头。响应体应始终带结构化错误信息（错误码、消息、请求 ID），供客户端定位问题。
> 缓存机制
> HTTP 缓存分为强缓存与协商缓存两类：
> 强缓存（不发请求，直接使用本地缓存）：
> `Cache-Control: max-age=3600` 相对时间（优先级高于 Expires）；
> `Expires` 绝对时间，受客户端时钟影响，已基本被替代。
> 协商缓存（发请求，由服务器判断是否可用缓存）：
> `ETag` + `If-None-Match`：服务器返回内容指纹（通常内容哈希），客户端下次携带该值，内容未变时服务器回 304 Not Modified（无响应体，省流量）；
> `Last-Modified` + `If-Modified-Since`：时间戳方案，精度秒级且编辑可能保持旧时间戳，可靠性不如 ETag。

### [ ] 条目 25（`python-GIL与多线程.md`）

**问题**：为什么 Python 的多线程在处理 CPU 密集型任务时反而更慢？

**AI 生成的答案**：因为 GIL 的存在，多个线程并行计算反而比单线程更慢——线程切换本身有开销，还得排队抢 GIL。

**出处段落**（检查答案是否确实出自此段）：

> Python GIL 与多线程
> GIL 是什么
> GIL（Global Interpreter Lock，全局解释器锁）是 CPython 解释器中的互斥锁：同一时刻只有一个线程能持有 GIL 并执行 Python 字节码。它是 CPython 的历史遗留设计——诞生于 1992 年，当时计算机只有单核 CPU，加锁可以简化解释器内部的内存管理（引用计数不需要原子操作）。如今多核普及，GIL 成为 Python 并行计算的著名瓶颈。
> GIL 的影响
> 1. CPU 密集型多线程无效：多个线程并行计算反而比单线程更慢——线程切换本身有开销，还得排队抢 GIL。典型例子是纯 Python 的大循环求和。
> 2. I/O 密集型多线程有效：线程在等待网络、磁盘等 I/O 时会释放 GIL，其他线程可以继续执行，因此多线程对爬虫、Web 请求这类场景提升明显。
> 3. 引用计数的内存管理不需要加锁，单线程代码的性能因此受益。
> 绕过 GIL 的方案
> **multiprocessing**：每个进程有独立的解释器和 GIL，真正利用多核。代价是进程间通信（pickle 序列化）有额外开销，内存占用翻倍。

### [ ] 条目 30（`python-生成器与迭代器.md`）

**问题**：用生成器写迭代器时，函数里出现什么关键字就可以让函数变成生成器？

**AI 生成的答案**：函数体中出现 yield 关键字时，调用该函数不会执行函数体，而是返回一个生成器对象。

**出处段落**（检查答案是否确实出自此段）：

> Python 生成器与迭代器
> 迭代器协议
> Python 中任何实现了 __iter__ 和 __next__ 方法的对象都是迭代器。__iter__ 返回迭代器自身，__next__ 每次调用返回下一个元素；当元素耗尽时抛出 StopIteration 异常，for 循环会自动捕获它并结束遍历。判断一个对象是否可迭代，可以用 collections.abc.Iterable 配合 isinstance。
> class Countdown:
> def __init__(self, n):
> self.n = n
> def __iter__(self):
> return self
> def __next__(self):
> if self.n <= 0:
> raise StopIteration
> self.n -= 1
> return self.n
> 生成器与 yield
> 生成器是编写迭代器最简洁的方式：函数体中出现 yield 关键字，调用该函数不会执行函数体，而是返回一个生成器对象。每次 next() 调用会让函数执行到下一个 yield 处暂停并返回值，函数状态（局部变量、执行位置）被完整保留，下次继续从暂停点恢复执行。这种"可暂停的函数"模型是 Python 协程的基础。

**出处段落**（检查答案是否确实出自此段）：

> Python 装饰器与闭包
> 闭包的定义
> 闭包指函数引用了定义它的外层作用域中的变量，且该函数在其外层作用域之外被调用时仍然"记住"这些变量。Python 中闭包形成的条件是：内层函数引用外层函数的局部变量，且外层函数返回内层函数。闭包捕获的是变量而非值——如果内层函数只读取变量，行为符合直觉；若要修改外层变量，需要用 nonlocal 声明。
> def make_counter():
> count = 0
> def counter():
> nonlocal count
> count += 1
> return count
> return counter
> 上面 counter 就是闭包，count 是它的自由变量。没有 nonlocal 时对 count 的赋值会被解释为创建局部变量，从而抛出 UnboundLocalError。
> 装饰器原理
> 装饰器本质是一个接受函数作为参数、返回新函数的高阶函数。@decorator 语法等价于 func = decorator(func)。装饰器在函数定义时执行（导入模块时），而不是调用时执行，这决定了装饰器常用于注册（如 Flask 的路由注册）而不是业务逻辑。

### [ ] 条目 45（`redis-缓存策略.md`）

**问题**：Redis为什么读写能那么快？它又是怎么把数据存到磁盘上的？

**AI 生成的答案**：Redis是内存键值存储，读写延迟在亚毫秒级（单线程处理命令，避免锁与上下文切换开销）。数据存在内存，通过RDB快照与AOF日志两种机制持久化到磁盘。

**出处段落**（检查答案是否确实出自此段）：

> Redis 缓存策略
> Redis 定位
> Redis 是内存键值存储，读写延迟在亚毫秒级（单线程处理命令，避免锁与上下文切换开销），常用作缓存、分布式锁、计数器、消息队列。数据存在内存，通过 RDB 快照与 AOF 日志两种机制持久化到磁盘。单线程模型下，慢命令（KEYS、大集合的 O(n) 操作）会阻塞整个服务，生产环境禁用 KEYS 改用 SCAN。
> 缓存读写模式
> 1. Cache Aside（旁路缓存）：读时先查缓存，未命中查数据库并回填缓存；写时直接更新数据库并删除缓存。最常见，逻辑简单，但对一致性只提供最终保证。
> 2. Read Through / Write Through：缓存层代理读写，应用不直接接触数据库。
> 3. Write Behind（写回）：先写缓存，异步批量刷回数据库，写入延迟最低，但宕机有数据丢失窗口。
> 缓存穿透、击穿、雪崩
> **穿透**：查询根本不存在的数据，缓存和数据库都无记录，每次请求都打到数据库。防御：布隆过滤器拦截不存在的 key、把空结果也短时缓存（空值缓存）。

### [ ] 条目 60（`数据库-索引与B树.md`）

**问题**：我有一个联合索引 (a, b, c)，查询条件写成 WHERE a = 1 AND c = 3 时，这个索引用得上吗？

**AI 生成的答案**：只能用上 a 列，因为中间断了 b，c 列无法使用索引。

**出处段落**（检查答案是否确实出自此段）：

> InnoDB 的聚簇索引（主键索引）把整行数据存在叶子节点，表本身按主键 B+ 树组织；二级索引（辅助索引）叶子存索引列 + 主键值，通过主键再回表查完整行。因此：主键应尽量短（二级索引叶子都在复制主键）、自增主键优于随机主键（自增是顺序追加，随机插入导致页分裂）。
> 最左前缀原则
> 联合索引 (a, b, c) 的 B+ 树按 a、b、c 的次序排序，因此只有查询条件以 a 开头才能利用索引：WHERE a = 1 可用，WHERE a = 1 AND b = 2 可用，WHERE b = 2 不能用（跳过了 a），WHERE a = 1 AND c = 3 只能用 a 列（中间断了 b）。范围条件之后的列同样失效。
> 常见失效场景
> 对索引列做函数运算或隐式类型转换（`WHERE YEAR(created_at) = 2026`）；
> 前导模糊匹配 `LIKE '%keyword'`（后缀通配符可以用）；
> 负向条件 `!=`、`NOT IN` 通常不走索引；
> 优化器判断回表代价太高时主动选择全表扫描（小表尤其如此）。
> 执行计划

**AI 生成的答案**：当装载因子超过 2/3 时，Python dict 会扩容，新容量约为原来的 2 倍，扩容时需要将所有键重新哈希迁移，单次扩容的复杂度是 O(n)，但均摊后插入操作仍是 O(1)。

**出处段落**（检查答案是否确实出自此段）：

> 装载因子 α = 元素数量 / 桶数量。α 过大会导致冲突加剧、性能退化；α 过小则浪费内存。Python dict 在 α 超过 2/3 时扩容（新容量约为原来的 2 倍），扩容时全部键重新哈希迁移，单次扩容 O(n)，但摊还分析后插入仍是 O(1)。攻击场景：不断触发扩容可造成性能抖动，即"哈希洪水攻击"，Python 3 用随机化哈希种子（每次进程启动随机生成）使攻击者难以预测下标。
> 哈希函数的要求
> 相同对象必须返回相同哈希值（`hash(a) == hash(b)` 若 `a == b`）；
> 相等的对象哈希必须相同，反之不成立——哈希相同可能只是冲突；
> 可变对象（如 list）不能作为 dict 的键，因为内容变化后哈希值会变，导致元素"丢失"。`tuple` 不可变所以可以作为键，但 tuple 内含 list 同样不行。
> 时间复杂度与陷阱
> 平均 O(1)，最坏 O(n)（全部键冲突成一条链）；
> 遍历 dict 的顺序是插入序（Python 3.7 起保证），不是键的大小序；

### [ ] 条目 70（`算法-二分查找.md`）

**问题**：用二分查找找第一个大于某个值的位置，判断条件应该怎么写？

**AI 生成的答案**：条件换成 nums[mid] > target，这是 upper_bound 的语义。

**出处段落**（检查答案是否确实出自此段）：

> 二分查找
> 适用条件与思想
> 二分查找（Binary Search）要求数组有序，每次比较中间元素与目标值，排除一半候选区间，时间复杂度 O(log n)。n = 10 亿时最多比较约 30 次，这是它相比线性查找 O(n) 的数量级优势。
> 标准实现与边界
> 最经典的写法是左闭右开区间 [lo, hi)：
> def binary_search(nums, target):
> lo, hi = 0, len(nums)
> while lo < hi:
> mid = (lo + hi) // 2
> if nums[mid] < target:
> lo = mid + 1
> elif nums[mid] > target:
> hi = mid
> else:
> return mid
> return -1  # 未找到
> 循环不变量：目标如果存在，一定在 [lo, hi) 内。mid = (lo + hi) // 2 在语言层面可能溢出（如 C 的 int 加法），安全写法是 lo + (hi - lo) // 2。
> 变形：查找边界
> **第一个 >= target 的位置**（lower_bound）：找到 `nums[mid] >= target` 时收缩 `hi = mid`，最后返回 `lo`。这是 C++ `std::lower_bound` 的语义。
> **第一个 > target 的位置**（upper_bound）：条件换成 `nums[mid] > target`。

### [ ] 条目 80（`算法-快速排序.md`）

**问题**：快速排序在什么情况下会退化到 O(n²) 的时间复杂度？

**AI 生成的答案**：最坏情况是每次 pivot 都取到最大或最小元素（如已排序数组 + 固定取端点），递归深度变为 n，退化为 O(n²)。

**出处段落**（检查答案是否确实出自此段）：

> 快速排序
> 基本思想
> 快速排序（Quicksort）由 Tony Hoare 于 1960 年提出，是分治思想的代表算法。每次选取一个基准元素（pivot），把数组划分为两个子区间：左边全部小于等于 pivot，右边全部大于 pivot，然后对两个子区间递归排序。划分完成时 pivot 已经落在最终位置上。
> 分区过程
> 以 Lomuto 分区为例：维护一个指针 i，表示"小于 pivot 区域的末尾"。遍历数组，遇到小于 pivot 的元素就与 i 位置交换并把 i 右移；遍历结束后把 pivot 换到 i 位置。一次分区的时间复杂度是 O(n)。
> def quicksort(arr, lo, hi):
> if lo >= hi:
> return
> p = partition(arr, lo, hi)   # 返回 pivot 的最终下标
> quicksort(arr, lo, p - 1)
> quicksort(arr, p + 1, hi)
> 时间复杂度
> **最好/平均情况**：每次划分都接近对半，递归深度约 log n，总时间 O(n log n)。
> **最坏情况**：每次 pivot 都取到最大或最小元素（如已排序数组 + 固定取端点），递归深度 n，退化为 O(n²)。
