# HTTP 状态码与缓存

## 状态码分类

- **1xx 信息**：请求已收到，继续处理（101 协议升级，WebSocket 握手）；
- **2xx 成功**：200 请求成功；201 已创建（POST 返回新资源）；204 无内容（删除成功但无响应体）；
- **3xx 重定向**：301 永久重定向（SEO 权重转移，浏览器会缓存）；302 临时重定向（历史兼容，POST 会被改成 GET 引发常见坑）；307/308 严格保留请求方法的重定向；
- **4xx 客户端错误**：400 参数错误；401 未认证（缺凭证）；403 已认证但无权限；404 资源不存在；405 方法不允许；429 请求过多（限流）；
- **5xx 服务端错误**：500 服务器内部错误；502 网关错误（上游无响应）；503 服务不可用（过载或维护）；504 网关超时（上游响应太慢）。

## 状态码设计实践

RESTful API 中状态码要区分语义：认证失败用 401 而不是 400；参数校验失败用 400 还是 422（Unprocessable Entity，语义是"格式对但内容不合法"）取决于团队规范；限流建议 429 并携带 `Retry-After` 头。响应体应始终带结构化错误信息（错误码、消息、请求 ID），供客户端定位问题。

## 缓存机制

HTTP 缓存分为强缓存与协商缓存两类：

**强缓存**（不发请求，直接使用本地缓存）：
- `Cache-Control: max-age=3600` 相对时间（优先级高于 Expires）；
- `Expires` 绝对时间，受客户端时钟影响，已基本被替代。

**协商缓存**（发请求，由服务器判断是否可用缓存）：
- `ETag` + `If-None-Match`：服务器返回内容指纹（通常内容哈希），客户端下次携带该值，内容未变时服务器回 304 Not Modified（无响应体，省流量）；
- `Last-Modified` + `If-Modified-Since`：时间戳方案，精度秒级且编辑可能保持旧时间戳，可靠性不如 ETag。

`Cache-Control` 常见指令：`no-store`（完全不缓存，交易数据）、`no-cache`（可缓存但每次必须协商）、`private`（仅浏览器缓存）、`public`（CDN 也可缓存）、`s-maxage`（CDN 专用过期时间）、`immutable`（内容永不变化，无需协商）。

## 缓存穿透与 CDN

资源 URL 带内容哈希（如 `app.a1b2c3.js`）+ `max-age=31536000, immutable`，内容更新时文件名变化即新 URL，从根上避开过期问题——这是前端构建工具（Webpack/Vite）的标准做法。CDN 边缘节点按 `Cache-Control` 缓存静态资源，回源请求大幅减少。

## 常见面试题点

- 304 与 200 的区别：304 无响应体，浏览器用本地缓存，省的是传输体积；
- 刷新（F5）会带上协商缓存头，Ctrl+F5 强制忽略缓存头发完整请求；
- POST 请求默认不缓存，GET 可缓存；带 `Authorization` 的响应默认 `private`。
