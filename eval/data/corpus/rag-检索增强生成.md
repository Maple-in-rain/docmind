# RAG 检索增强生成

## 定义

RAG（Retrieval-Augmented Generation，检索增强生成）在大型语言模型生成答案之前，先从外部知识库检索相关片段，把片段作为上下文拼入提示词，让模型基于检索结果作答。它解决了 LLM 的三个痛点：训练数据截止导致的知识陈旧、私有领域知识缺失、以及幻觉（模型编造事实）。

## 标准流水线

1. **文档解析**：PDF/Word/Markdown 等多格式提取纯文本；
2. **分块（Chunking）**：按固定窗口或标题结构切分，块间留重叠防止语义被切断；
3. **向量化（Embedding）**：调用 embedding 模型把块文本编码为高维向量；
4. **入库**：向量写入向量数据库（Chroma/Milvus/FAISS），文本与元数据存关系库；
5. **检索**：查询向量化后做相似度检索（余弦/内积），取 top-k；
6. **生成**：检索片段 + 系统提示 + 用户问题拼成 prompt，LLM 生成答案，附带引用编号。

## 为什么需要混合检索

纯向量检索擅长语义近似（"怎么快速排序"能命中排序算法文档），但弱于精确关键词：专有名词、缩写、代码符号（如 "O(n)"、"GIL"）在 embedding 空间中经常失配。BM25 基于词频统计，对精确词匹配敏感，但理解不了同义改写。混合检索同时跑两路，用 **RRF（倒数排名融合）** 合并排名——`score = Σ 1/(k + rank_i)`，k 通常取 60——只融合排名不融合分数，因为两路分数不同量纲。

## 重排（Rerank）

双塔 embedding 模型为了快速检索牺牲了交互精度；重排用 cross-encoder（如 bge-reranker）把查询与每个候选文档拼接后完整编码，排序质量显著更高，但计算开销大，因此只在检索召回的小候选集（如 top-20）上运行，不跑全库。工程口诀："宽召回、精排序"。

## 评估指标

- **recall@k**：前 k 个结果中命中的相关文档比例——衡量"找没找全"；
- **MRR@k**：首个相关文档排名倒数的平均——衡量"找得快不快"；
- 好的评估需要测试集：让 LLM 从语料反向生成"答案在原文中"的问题，人工抽查修正，再用网格实验（分块大小 × 重叠 × 策略 × 重排）比较配置。

## 常见优化

- **上下文缓存**：系统提示与检索片段放消息头部，命中 LLM 的 KV 缓存降低费用；
- **多轮指代消解**：把"它和归并排序比呢"改写成完整问题再检索；
- **小到大检索**：先检索小块定位，再合并成完整上下文；
- **引用溯源**：答案中标注片段编号，前端渲染来源卡片，建立用户信任。

## 局限性

RAG 效果受限于检索质量：检索失败则答案失败（garbage in, garbage out）。分块策略、embedding 模型选型、重排与否都会显著影响指标，这也是"检索质量工程"存在的意义——用数据而不是直觉做决策。
