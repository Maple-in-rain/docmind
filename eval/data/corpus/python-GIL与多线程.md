# Python GIL 与多线程

## GIL 是什么

GIL（Global Interpreter Lock，全局解释器锁）是 CPython 解释器中的互斥锁：同一时刻只有一个线程能持有 GIL 并执行 Python 字节码。它是 CPython 的历史遗留设计——诞生于 1992 年，当时计算机只有单核 CPU，加锁可以简化解释器内部的内存管理（引用计数不需要原子操作）。如今多核普及，GIL 成为 Python 并行计算的著名瓶颈。

## GIL 的影响

1. **CPU 密集型多线程无效**：多个线程并行计算反而比单线程更慢——线程切换本身有开销，还得排队抢 GIL。典型例子是纯 Python 的大循环求和。
2. **I/O 密集型多线程有效**：线程在等待网络、磁盘等 I/O 时会释放 GIL，其他线程可以继续执行，因此多线程对爬虫、Web 请求这类场景提升明显。
3. 引用计数的内存管理不需要加锁，单线程代码的性能因此受益。

## 绕过 GIL 的方案

- **multiprocessing**：每个进程有独立的解释器和 GIL，真正利用多核。代价是进程间通信（pickle 序列化）有额外开销，内存占用翻倍。
- **C 扩展**：在 C 代码中显式释放 GIL，让计算在其他线程执行 Python 时并行进行。NumPy 的矩阵运算就是这么做的。
- **asyncio 协程**：单线程事件循环，靠协作式调度并发处理 I/O，根本不需要多线程。
- 其他实现：Jython（JVM 上）与 IronPython 没有 GIL；CPython 官方在 3.13 引入了 GIL 的移除计划，但作为可选项，默认仍开启。

## 线程安全与锁

即使有 GIL，Python 多线程也**不保证**代码线程安全：GIL 只保证字节码执行的原子性，一行 Python 语句可能对应多条字节码，线程可能在中间被切换。因此共享可变状态仍需要 `threading.Lock`、`RLock` 或 `queue.Queue` 等同步原语。经典例子：`count += 1` 在多线程下会丢失更新。

## 常见误区

"Python 多线程没用"是常见误解，准确说法是：**CPU 密集型**任务应选 multiprocessing 或 asyncio + C 扩展，**I/O 密集型**任务用多线程完全合适。判断方法：观察任务瓶颈在 CPU 还是等待外设。
