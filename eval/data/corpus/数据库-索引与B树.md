# 数据库索引与 B+ 树

## 为什么需要索引

没有索引时数据库只能全表扫描：查找一行平均要读一半的数据页，表越大越慢。索引是"排好序的快速查找结构"，把 O(n) 的查找降为 O(log n)。代价是写入变慢（每次插入/删除要维护索引）和额外的磁盘占用，因此索引不是越多越好。

## B+ 树结构

关系型数据库（MySQL InnoDB、PostgreSQL）默认索引结构是 B+ 树：

- 多叉平衡树，所有数据都存在**叶子节点**，叶子按序用指针串联成链表；
- 非叶子节点只存键值作为"路标"，不存数据；
- 每个节点对应一个磁盘页（常见 16KB），一次磁盘 I/O 读入一个节点。

B+ 树比二叉搜索树适合磁盘的原因：树的高度低（千万行数据只需 3~4 层，即 3~4 次 I/O），且叶子链表天然支持范围查询。B 树（B-Tree）与 B+ 树的区别在于数据是否只放在叶子层——B 树节点本身存数据，随机查询可能更早命中；B+ 树所有查找路径等长，且叶子链表让范围扫描高效。

## 聚簇索引与二级索引

InnoDB 的**聚簇索引**（主键索引）把整行数据存在叶子节点，表本身按主键 B+ 树组织；**二级索引**（辅助索引）叶子存索引列 + 主键值，通过主键再回表查完整行。因此：主键应尽量短（二级索引叶子都在复制主键）、自增主键优于随机主键（自增是顺序追加，随机插入导致页分裂）。

## 最左前缀原则

联合索引 `(a, b, c)` 的 B+ 树按 a、b、c 的次序排序，因此只有查询条件以 a 开头才能利用索引：`WHERE a = 1` 可用，`WHERE a = 1 AND b = 2` 可用，`WHERE b = 2` 不能用（跳过了 a），`WHERE a = 1 AND c = 3` 只能用 a 列（中间断了 b）。范围条件之后的列同样失效。

## 常见失效场景

- 对索引列做函数运算或隐式类型转换（`WHERE YEAR(created_at) = 2026`）；
- 前导模糊匹配 `LIKE '%keyword'`（后缀通配符可以用）；
- 负向条件 `!=`、`NOT IN` 通常不走索引；
- 优化器判断回表代价太高时主动选择全表扫描（小表尤其如此）。

## 执行计划

用 `EXPLAIN` 查看一条 SQL 的执行计划：`type` 列从好到差依次是 const、eq_ref、ref、range、index、ALL；`key` 显示实际使用的索引；`rows` 是预估扫描行数。`type = ALL` 即全表扫描，是慢查询排查的第一个信号。

## 其他索引结构

- **哈希索引**：等值查询 O(1)，但不支持范围查询，Memory 引擎使用；
- **倒排索引**：全文检索用，词 → 文档列表映射（Lucene/Elasticsearch 的核心结构）；
- **LSM 树**：写入先落内存再顺序刷盘，写优化，LevelDB/RocksDB 使用。
